# ADR-0011: GUI実装の簡略化と既存開発環境の維持

- **ステータス**：採用
- **決定日**：2026-11-02
- **対象**：our-taskdepot
- **関連ADR**：ADR-0001（GUI技術選定）
- **関連Issue**：#6、#7、#9、#11、およびGUI先行実装Issue

## 1. コンテキスト（背景）

our-taskdepotは、C言語初学者向けのコンパイルエラー解説ツールである。

現在、Windows 11上で動作するネイティブアプリケーションとして開発しており、GUIにはWin32 APIを使用する方針を採用している。

しかし、Win32 APIによるGUIの直接実装には、ウィンドウ生成、メッセージ処理、画面部品の配置など、C言語初学者にとって難易度の高い作業が含まれる。

GUIを担当する2人のメンバーは、バックエンドの完成を待たずに、ダミー動作を備えた画面を先行実装する予定である。

この状況で新しいGUIライブラリを導入すると、依存関係の追加、ビルド設定の変更、開発環境の再構築が必要になる可能性がある。

既存の開発環境はすでに構築・検証済みであり、発表会までの限られた期間では、環境構築よりもアプリケーションの実装に時間を割くことを優先する。

## 2. 決定

**Win32 APIを維持し、GUIの実装方法と初期機能を簡略化する。**

具体的には、以下の方針を採用する。

### 2.1 GUI技術

- GUIの基本技術にはWin32 APIを使用する。
- 新しいGUIフレームワークは導入しない。
- Visual Studioのリソースエディタを利用可能な場合、画面部品の視覚的な配置に活用する。
- リソースエディタの利用を必須とはせず、通常のWin32 APIによる実装も許容する。
- 既存のCMake・Ninja・MSVC環境を維持する。

### 2.2 コードエディタ

初期実装では、Windows標準の複数行テキスト入力コントロールを使用する。

必要な機能は以下とする。

- 複数行のソースコード入力
- 文字の追加・削除
- コピー・貼り付け
- 入力内容の取得と更新

行番号、構文ハイライト、コード補完などの高度な編集機能は初期実装の必須要件としない。

既に導入済みのScintillaは削除せず、後続の機能改善で利用するか判断する。

### 2.3 GUIの先行実装

バックエンドが未完成でもGUIを動作確認できるよう、ダミーデータを使用する。

最低限、以下の状態を再現する。

- コンパイル処理中
- コンパイル成功
- コンパイル失敗
- 日本語エラー解説表示
- 未対応エラー表示
- 複数エラー発生時の残り件数表示
- プログラム実行成功・失敗

初期段階では実際のコンパイラやプログラムを起動しない。

### 2.4 バックエンドとの分離

GUIとバックエンドの処理は分離する。

GUI側は、あらかじめ定義したインターフェースを通じて処理要求を発行し、結果データを受け取る構成とする。

ダミー処理と実際のバックエンド処理は、可能な限り共通のデータ形式を使用する。

これにより、後続の統合工程では、GUIの大幅な変更を伴わずにダミー処理を実処理へ置き換えられる構造を目指す。

共通データ構造・公開関数・モジュールの責務は、別途インターフェース仕様書で定義する。

### 2.5 GUI担当者の分担

GUIは2人で並行開発する。

**担当A：画面構成・入力操作**

- メインウィンドウ
- 基本レイアウト
- コード入力欄
- コンパイル・実行ボタン
- 標準入力欄

**担当B：結果表示・ダミー処理**

- コンパイル結果表示
- 日本語エラー解説表示
- 診断メッセージ表示
- 標準出力・標準エラー出力表示
- ダミーデータと画面状態の切り替え

共有する関数・データ構造・変更対象ファイルについては、実装開始前に共通仕様を定義する。

各担当者は共通仕様に従って実装し、その変更が必要な場合はリーダーに確認する。

## 3. 検討した代替案

### 案A：Win32 APIを直接使用する（採用技術）

追加ライブラリが不要であり、既存の開発環境を利用できる。

一方、ウィンドウ生成やイベント処理などの実装難易度が高い。

**判断：採用。** リソースエディタの活用と機能の段階的実装によって負担を軽減する。

### 案B：libui-ng

C言語向けのGUIライブラリであり、比較的少ないコードでGUIを構築できる。

一方、既存環境への依存関係追加とビルド統合の検証が必要になる。

**判断：不採用。** 今回は実装環境の維持を優先する。

### 案C：IUP

C言語向けのGUIツールキットであり、簡潔なAPIを提供する。

一方、開発・保守状況と新たな依存関係の管理が懸念される。

**判断：不採用。** 既存環境を維持する方針に適さないため。

### 案D：Scintillaを初期段階から組み込む

コード編集に適した高度な機能を利用できる。

一方、通常のテキスト入力欄よりも組み込みと制御が複雑になる。

**判断：初期実装では採用しない。** 将来の改善候補として維持する。

## 4. 決定による影響

### メリット

- 新規GUIライブラリの導入が不要になる。
- 既存の開発環境を維持できる。
- GUI担当者の学習範囲を限定できる。
- バックエンドと並行してGUIを開発できる。
- ダミー動作によって早期に操作確認ができる。
- 高度なエディタ機能に時間を使わず、主要機能の実装を優先できる。

### デメリット・制約

- Win32 API特有のメッセージ処理などは依然として必要になる。
- 画面レイアウトの変更に手間がかかる可能性がある。
- 初期段階では構文ハイライトや行番号を利用できない。
- ダミー処理と実際のバックエンドを接続するためのインターフェース設計が必要になる。
- リソースエディタの利用方法によっては、画面定義ファイルとCMakeの連携を確認する必要がある。

## 5. 実装上の制約

- C言語を維持する。
- Windows 11を対象とする。
- 既存の開発環境を原則変更しない。
- 新しいGUIライブラリを追加しない。
- 既存のADRで確定しているGUI以外の技術選定を変更しない。
- ダミー処理とGUI表示処理を分離する。
- 実際のバックエンド接続は後続Issueで実施する。
- 共有インターフェースの無断変更を禁止する。

## 6. 完了判定

本ADRに基づく初期GUI実装は、次の条件を満たしたときに完了とする。

- [ ] Windows 11上でGUIが起動する。
- [ ] C言語ソースコードを入力・編集できる。
- [ ] コンパイル・実行ボタンを操作できる。
- [ ] ダミーのコンパイル結果と日本語解説を表示できる。
- [ ] ダミーのプログラム実行結果を表示できる。
- [ ] GUIとダミー処理が分離されている。
- [ ] バックエンド接続用のインターフェースが定義されている。
- [ ] 既存のCMake環境でビルドできる。
- [ ] 既存テストが成功する。
- [ ] 新しいGUIライブラリを追加していない。

## 7. 関連ADRとの関係

本ADRは、ADR-0001で選定したWin32 APIを維持しつつ、GUIの初期実装範囲を簡略化する補足決定である。

Scintillaが既存ADRで採用決定済みの場合、初期実装への組み込みを延期する点について、本ADRを優先する。

それ以外の既存技術選定は変更しない。

## 8. 将来の見直し条件

次のいずれかが発生した場合、GUIの技術選定や実装範囲を再検討する。

- 標準テキスト入力欄では必須要件を満たせなくなった場合
- Win32 APIによる実装負担が想定を大幅に超えた場合
- Scintillaの高度な編集機能が必要になった場合
- GUIとバックエンドの接続方式に設計上の問題が見つかった場合

技術変更が必要になった場合は、新しいADRによって判断を記録する。
