# ADR-0009：GitHub運用とコードレビュー方針

**ステータス：採用**

**決定日：2026年10月27日**

## 背景

本プロジェクトは6人で開発するC言語アプリケーションである。

メンバーのGit・GitHub経験には差があり、チーム開発が初めてのメンバーもいる。

そのため、複雑な運用を避けながら、コードの品質と変更履歴を管理できる仕組みが必要である。

## 検討した選択肢

- GitHub Flow + 持ち回りレビュー
- GitHub Flow + リーダーによる全件レビュー
- GitHub Flow + ペア固定レビュー

## 決定

GitHub Flowを採用し、Pull Requestのレビューはメンバー間で持ち回りとする。

### ブランチ運用

- `main`を統合用ブランチとする。
- `main`への直接pushは禁止する。
- 作業ごとにブランチを作成する。
- Pull Requestを通じて`main`へ統合する。
- マージ後、不要になった作業ブランチは削除する。

ブランチ名は以下の形式を基本とする。

- `feature/xxx`：機能追加
- `fix/xxx`：不具合修正
- `docs/xxx`：文書の変更
- `test/xxx`：テスト追加・修正

### Pull Request

すべての変更は原則としてPull Requestを通じて統合する。

Pull Requestには以下を記載する。

- 変更内容
- 関連するIssue
- 動作確認・テスト結果
- レビューしてほしい点

### コードレビュー

- 原則として1人以上のレビュー承認を必要とする。
- レビュー担当は持ち回りで決定する。
- 作成者自身による承認は認めない。
- 難易度の高い変更や共通インターフェースの変更は、リーダーも確認する。
- レビュー担当者が理解できない箇所は、作成者に説明を求める。
- 修正が必要な場合は、理由を添えてコメントする。

### マージ条件

以下を満たした場合にマージできる。

- 必要なレビュー承認を得ている。
- ビルドが成功する。
- 関連するテストが成功する。
- 未解決の重大な問題がない。

自動テストが未整備の初期段階では、実施した手動確認をPull Requestに記録する。

### Issue管理

作業はGitHub Issuesで管理する。

Issueには、作業内容と完了条件を明記する。

初学者でも取り組みやすいように、原則として1〜3日程度で完了できる単位に分割する。

## 決定理由

- GitHub Flowは比較的単純で、初学者にも説明しやすい。
- Pull Requestによって変更内容を確認してから統合できる。
- 持ち回りレビューにより、特定のメンバーへの負担集中を避けられる。
- 全員が他者のコードを読む経験を積める。
- IssueとPull Requestを関連付けることで、進捗を把握しやすくなる。

## 懸念点と対応

### Git未経験者の操作ミス

最初にブランチ作成からPull Request作成までの練習を行う。

必要に応じてGUIツールの使用を認める。

### レビュー品質のばらつき

共通のレビューチェックリストを用意する。

レビューでは、コードの正しさだけでなく、処理内容を理解できるかどうかも確認する。

### リーダーへの負担集中

通常の変更はメンバー間でレビューする。

共通基盤や重要な設計変更のみ、リーダーが重点的に確認する。
