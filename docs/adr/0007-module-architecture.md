# ADR-0007：アプリケーション内部のモジュール構成

**ステータス：採用**

**決定日：2026年10月27日**

## 背景

本アプリケーションは、C言語初学者向けのコンパイルエラー解説ツールである。

GUI、コンパイラ制御、エラー解析、解説データ管理、プログラム実行など、複数の機能から構成される。

また、複数人によるチーム開発を行うため、作業範囲を明確にし、各機能を独立して実装・テストできる構造が求められる。

## 検討した選択肢

- 機能別モジュール構成
- レイヤー別構成
- 単一ファイル中心の構成

## 決定

機能別モジュール構成を採用する。

以下の機能を、それぞれ独立したモジュールとして分割する。

- GUI：Win32 APIとScintillaによる画面表示・操作
- コンパイラ制御：LLVM-MinGWの起動とコンパイル結果の取得
- エラー解析：診断メッセージの解析とパターン照合
- 解説データ管理：JSONファイルの読み込みと検証
- 実行制御：生成したプログラムの起動と標準入出力の管理

## 決定理由

- 機能ごとの責務が明確になる。
- 複数人で作業を分担しやすい。
- 同じソースファイルへの変更が集中しにくくなる。
- GUIと内部処理を分離できる。
- 各機能を個別にテストしやすい。
- 必要な機能だけを変更・拡張しやすい。

## 設計方針

### モジュール間の連携

各モジュールの公開インターフェースは、ヘッダーファイルで定義する。

他モジュールの内部実装に直接依存しないようにする。

### GUIと内部処理の分離

コンパイラ制御、エラー解析、解説データ管理などの処理は、GUIに依存しない形で実装する。

GUIから内部処理を呼び出し、結果を受け取って表示する。

### インターフェースの事前合意

複数のメンバーが別々のモジュールを担当する場合、実装前に必要な関数、引数、戻り値、データ構造を共有する。

### テスト

可能な限り、GUIを起動せずに各モジュールをテストできる構成とする。

### 依存関係

モジュール間の循環依存を避ける。

共通して使用する型や定数が必要になった場合は、共通ヘッダーへの分離を検討する。

## 懸念点と対応

### モジュール間の仕様不一致

担当者ごとに異なるデータ構造を想定すると、結合時に問題が発生する。

公開インターフェースを事前に合意し、変更時は関係する担当者と共有する。

### 分割のしすぎ

細かく分割しすぎると、ファイル数や依存関係が増えて理解しづらくなる。

初期段階では必要最小限の分割とし、機能の成長に応じて調整する。

- 公開ヘッダーと共通データ構造を設計する。

- モジュールごとの担当者を決める。
- モジュール単位のテスト方針を定める。
